# Step 06 — DB schema v1 and row-level security

**Phase:** Phase 1 — Foundations
**PRD refs:** §7, §9
**Depends on:** 05
**Branch:** `stage1/06-db-schema-rls`

## Goal
Identity and tenancy tables, with RLS enforced by Postgres and not only by the code.

## Scope
**In**
- Drizzle schema and migrations: users, sessions, recovery_codes, organisations, memberships, invitations, audit_log (uuid v7, citext, timestamptz)
- Better Auth's required tables mapped onto these, with adapter fields reconciled
- `app_user` role without BYPASSRLS; RLS policies on tenant tables keyed on `current_setting('app.org_id')`
- audit_log: INSERT and SELECT only
- ~~Seed script for a Platform Admin~~ moved to Step 07 (needs Better Auth's password hashing)

**Out**
- Clients and scans tables (later steps)

## Files / packages touched
- apps/api/src/db/**, migrations

## Reuse from current code
- `withOrg` from Step 05

## Acceptance
- [x] Migrations apply on a fresh DB and re-running is a no-op (Drizzle has no down migrations; rollback = forward-fix migration or restore, see Notes)
- [x] A test proves org B can't see org A's rows with the app role, even with a hand-written query
- [x] UPDATE and DELETE on audit_log are refused

## Notes
Done 2026-11-20.
- **Tables** (`apps/api/src/db/schema.ts`): users, sessions, accounts, verifications, two_factors, organisations, memberships, invitations, audit_log.
  - The shape follows Better Auth 1.7.26's data model, checked with `getAuthTables` for the organisation and two-factor plugins. JS keys use Better Auth's field names and SQL columns use the PRD's snake_case names, so Step 07 can map each model by name.
  - Extra PRD columns: `users.is_platform_admin`; `organisations.legal_name/address/phone/dpco_licence_no/licence_status/licence_note/verified_by/verified_at/branding/deleted_at`; `memberships.invited_by`.
  - Enums: member_role (owner, admin, analyst, viewer), licence_status (unsubmitted, pending, verified, rejected), invitation_status, actor_type. Emails are citext. Every id defaults to a SQL `uuidv7()`.
- **Migrations** (`apps/api/drizzle/`):
  - `0000_bootstrap` (hand-written): citext and pgcrypto, `uuidv7()`, `app_current_org()` (NULL when unset, so policies fail closed), and the NOLOGIN roles `ndpa_api` and `ndpa_auth`.
  - `0001_identity_tables`: generated by drizzle-kit.
  - `0002_rls_and_grants` (hand-written): ENABLE and FORCE RLS on organisations, memberships, invitations and audit_log. `ndpa_api` policies use `org_id = app_current_org()` (`id = …` on organisations). `ndpa_auth` gets full access to identity tables and INSERT-only on audit_log. `ndpa_api` sees only users(id, name, email, image, email_verified, two_factor_enabled) and nothing on sessions, accounts, verifications or two_factors. No role can UPDATE or DELETE audit_log.
- **Scripts:**
  - `pnpm --filter api db:migrate` runs as the owner via `MIGRATION_DATABASE_URL`.
  - `db:roles` gives the two roles LOGIN and passwords from `DB_API_PASSWORD` and `DB_AUTH_PASSWORD`. The SQL is built with `format(%I, %L)`, so no secret is stored in a migration.
  - `db:setup` runs both. `.env.example` has the three database URLs.
  - The API's `DATABASE_URL` is now `ndpa_api`.
- **Proof:**
  - `pnpm test` (api): 27 passed, 13 of them new RLS tests on Testcontainers.
    - With no org set, all 4 tables return 0 rows.
    - Org A sees only its own rows, and asking for org B by id returns nothing.
    - Inserts, moves, updates and deletes into org B are rejected or affect 0 rows.
    - `ndpa_api` is denied on sessions, accounts, verifications, two_factors, `select * from users` and `is_platform_admin`.
    - The same holds through Drizzle, and the setting is gone after the transaction.
    - audit_log UPDATE, DELETE and (for ndpa_auth) SELECT are denied, while INSERT works for both roles.
    - Migrations are idempotent, ids are valid uuid v7, and neither role is superuser or has BYPASSRLS.
  - Dev: `db:setup` on `pnpm dev:infra`, then `\dt` lists 9 tables. The API ran as `ndpa_api` and health returned ok.
- **Deviations to know about:**
  1. Better Auth stores **session tokens unhashed** in `sessions.token`, where PRD §7 says "token stored hashed". It has no option to hash them; it can hash verification identifiers, which Step 07 turns on. Mitigation: only `ndpa_auth` can read sessions. **Owner decision pending:** accept this, or add a custom session layer later.
  2. Recovery codes are stored **encrypted** in `two_factors.backup_codes` (Better Auth's model) instead of a hashed `recovery_codes` table.
  3. `users.email_verified` is a boolean (Better Auth) rather than `email_verified_at`. The verification time is recorded in the audit log in Step 07.
  4. There are no down migrations (Drizzle). Rollback is a forward-fix migration or a restore (PITR in Step 33).
  5. Memberships have their own `id` (Better Auth) plus a unique `(org_id, user_id)`, where the PRD had a composite primary key.
- The Platform Admin seed moved to Step 07, which has the password hashing.
